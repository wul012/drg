# DRG 协同平台优化建议

## 0. 文档定位

本文档是在完成《功能与完成度分析》、三轮主动增强以及本地微型LLM接入之后，针对项目**后续可选的优化方向**做的系统梳理。

它**不是待办清单**，而是按工程分层给出的可选演进路径，供后续根据是否继续发展本项目、是否面向真实场景落地，按优先级分批推进。

每一条建议都对应了当前代码中的具体文件或函数，避免空泛。

---

## 1. 当前基线回顾

当前项目已具备：

- 完整业务闭环：需求分析 → DRG 入组 → 文档生成 → 测试用例 → 提交 → 移动端上报
- 8 个教学版 MDC 大类与对应 ADRG 规则，并支持 JSON 样例分组与无编码样例自动补码
- 角色权限（管理员 / 医生 / 分析员）与管理员病例撤销
- 病例多字段筛选、分页排序、虚拟文档下载、仪表盘分布可视化
- 本地微型LLM：覆盖 DRG 原因说明、需求分析、文档正文、测试文案，支持三档模式与外部语料文件
- 15 条 DRG 规则测试 + 9 条病例辅助函数测试 + 5 条本地微型LLM测试 + 冒烟测试
- Playwright 全链路调试验证记录 + 多份中文文档

单从"课程交付 / 答辩样机"维度看，已达可交付水位。

本文档讨论的是：**如果继续把它工程化、长期维护，还有哪些可以优化。**

## 3. 架构层优化

### 3.1 现状

- `app.py` 仍超过 1800 行，单文件同时承担：
  - 路由注册
  - 业务流程
  - 数据访问
  - 规则定义（`SIMPLIFIED_MDC_RULES` / `SIMPLIFIED_ADRG_RULES`）
  - 种子数据
  - 模板上下文注入
  - 本地微型LLM模式读取与会话协同
- 虽然病例筛选、分页、下载、分布和本地微型LLM接线已经逐步拆出了一部分辅助函数，但**文件级复杂度仍在持续上升**。

### 3.2 建议

- **按领域拆分 Blueprint**
  - `auth`（登录、注册、登出）
  - `cases`（DRG 入组、筛选、删除）
  - `documents`（列表、下载）
  - `dashboard`（分布、统计）
  - `agents`、`submit`、`mobile`
- **或按水平分层拆分模块**
  - `routes/`：只做请求解析与模板渲染
  - `services/`：业务流程（入组、筛选、分布计算）
  - `repositories/`：SQL 查询与映射
  - `rules/`：DRG 规则与规则匹配
  - `models/`：数据结构（dataclass / TypedDict）
- **推进顺序**
  1. 先抽 `rules/`（纯函数，无副作用，迁移最安全）
  2. 再抽 `repositories/`（集中 SQL，不改业务行为）
  3. 最后拆 Blueprint（涉及 URL 路由，放在最后）

### 3.3 预期收益

- 单文件行数显著下降
- 规则引擎可独立演进、独立测试
- 新增领域不再需要侵入 `app.py`

## 4. 数据与持久化层优化

### 4.1 现状

- SQL 完全手写，`drg_cases` 的 INSERT 列出 23 个字段，极易漏填。
- `drg_cases` 表存在**字段冗余**：`note` 与 `group_reason` 存储同一段文本（见 `build_case_record` 返回值）。
- 事务边界和业务逻辑混在同一个路由函数里，例如 `cases_page` 同时负责表单校验、入库、下游同步、commit。
- 数据库连接通过 `g.db` 管理已经足够，但缺少"只读视图 / 写事务"的显式区分。

### 4.2 建议

- **引入轻量 ORM 或自建 Repository**
  - SQLAlchemy Core（不用 ORM Session，只用表定义 + execute）是最小侵入选项
  - 或保持 sqlite3，但把每张表封装成 `XxxRepository` 类
- **去除字段冗余**
  - 保留 `group_reason`，从业务层直接派生 `note`，或者二者合一
  - 迁移时提供一次性脚本 + 兼容窗口
- **统一病例结构**
  - 用 `@dataclass` 或 `TypedDict` 定义 `DrgCase`，让 `get_drg_cases`、`build_case_record`、模板消费的都是同一个结构
  - 这一步同时受益于 §3 的 `models/` 抽离
- **事务显式化**
  - 业务函数声明自己是"写"还是"读"
  - commit 统一在服务层末尾，而不是路由里散落

### 4.3 预期收益

- 字段增删不再"一改七处"
- 单元测试可以直接构造 `DrgCase` 对象，无需走 SQLite
- 路由函数变薄

## 5. 业务规则层优化

### 5.1 现状

- DRG 规则硬编码在 `app.py` 顶部：
  - `SIMPLIFIED_MDC_RULES`
  - `SIMPLIFIED_ADRG_RULES`
  - `SIMPLIFIED_MCC_CODES` / `SIMPLIFIED_CC_CODES`
- 本地微型LLM的生成逻辑与模式参数集中在 `local_llm.py`：
  - `MODE_PROFILES`
  - `TASK_TOKEN_SETTINGS`
  - `local_llm_corpus.json`
- **扩 DRG 规则 = 改源码 = 重启服务**；扩本地微型LLM语料虽然已可改 JSON，但仍然需要重启进程才会生效。
- 当前 `generate_drg_reason` 等函数中，结构化业务事实和表达风格仍有一定耦合。
- 单元测试 `tests/test_drg_rules.py` 直接断言字面量（如 `"MDCE"`、`"FB1"`），规则与测试强耦合。

### 5.2 建议

- **规则外置**
  - 把 MDC / ADRG / CC / MCC 迁移到 `instance/rules/*.json` 或 `data/rules/*.yaml`
  - 服务启动时加载，也可暴露 `/admin/rules/reload` 做热更新（仅管理员）
- **本地微型LLM配置继续外置与版本化**
  - 给 `local_llm_corpus.json` 增加 schema 约束、版本号和字段校验
  - 将模式参数（如 `MODE_PROFILES` / `TASK_TOKEN_SETTINGS`）逐步迁移到配置文件，而不是继续只写在 Python 常量里
  - 提供启动时校验和管理员热重载入口，避免语料写坏后只能靠运行时报错定位
- **规则版本化**
  - 每份规则文件带 `version`、`effective_date`
  - 入组结果写入当时使用的规则版本，便于审计和回溯
- **事实层与表达层分离**
  - 先固定结构化事实槽位：主诊断、主手术、并发症层级、风险等级、状态
  - 再让本地微型LLM只负责“表达壳”的润色，避免文风增强时影响核心事实稳定性
- **规则数据集**
  - 建立 `tests/data/drg_cases.json` + `tests/data/drg_expected.json`
  - 用参数化测试跑全量，避免一个 assert 一个用例
- **文案金样回归**
  - 为 `strict / balanced / creative` 三档模式建立 golden snapshot
  - 每次调整语料或模式参数，都能对比差异，防止文案质量无感回退
- **规则 DSL（远期）**
  - 若未来需要真实的 CHS-DRG 规则，考虑用简化的 DSL 描述而不是 Python 条件分支

### 5.3 预期收益

- 新增 MDC 无需改 Python
- 规则可由非开发者维护（业务人员可改 JSON）
- 测试驱动的规则演进流程更清晰

## 6. 前端与交互优化

### 6.1 现状

- 分布图颜色映射已经由后端下发 `track_class`，模板条件分支明显减少。
- `/cases` 页的"最新结果"卡片已经随筛选集合联动，不再固定读取全量最新病例。
- 病例列表已经支持分页、排序以及 `MDC / 风险 / 状态 / 关键词` 组合筛选。
- 当前仍缺少时间范围、每页条数、快捷筛选预设，以及跨页面保留筛选状态。

### 6.2 建议

- **筛选条组件化**
  - 把 `/cases` 页筛选条抽成模板片段或宏，避免字段和样式继续堆在一个模板里
  - 统一 query 参数的序列化、回填与分页 URL 拼装逻辑
- **筛选维度继续扩展**
  - 在现有 `mdc`, `risk`, `status`, `q`, `sort` 基础上增加 `date_from`, `date_to`, `size`
  - 增加“只看需复核 / 只看高风险”等快捷预设
- **筛选语义显式化**
  - 在“最新DRG入组输出”附近提示：当前结果基于全量还是当前筛选集合
  - 避免用户把“当前页第一条”和“当前筛选集最新一条”混淆
- **列表可读性增强**
  - 关键词高亮
  - 当前筛选条件胶囊展示
  - 空结果时提供一键清空筛选
- **图表升级（可选）**
  - 当前纯 CSS 分布条足够教学场景
  - 若要交互，可接 ECharts / Chart.js，并保持纯 CSS 作为降级方案

### 6.3 预期收益

- 列表可伸缩到上千条病例
- "最新"与"当前视图"语义一致
- 配色逻辑不再散落在模板

## 7. 测试与质量保障优化

### 7.1 现状

- `tests/test_drg_rules.py` 15 条断言覆盖规则核心，质量较好。
- `tests/test_case_helpers.py` 已覆盖筛选、排序、分页和分布计算等辅助函数。
- `tests/test_local_llm.py` 已覆盖本地微型LLM的核心事实保持、模式规范化和外部语料元信息。
- `smoke_test.py` 是一条很长的集成路径，任一步失败都会影响后续断言定位。
- Playwright 已做过一次从首页到提交中心的全链路验证，但还没有沉淀为仓库内可重复执行的断言化 E2E 用例。
- 没有覆盖率度量。

### 7.2 建议

- **迁移到 pytest**
  - `smoke_test.py` 拆成多个 `test_*` 函数，共享 fixture
  - 单次失败可精确定位到具体 case
- **补本地微型LLM回归测试**
  - 增加 strict / balanced / creative 三档模式的 golden snapshot
  - 增加“语料损坏 / 缺字段 / JSON 不合法”时的降级与告警测试
- **引入覆盖率**
  - `pip install coverage`，CI 里执行 `coverage run -m pytest && coverage report`
  - 设定最低阈值（如 70%）作为门槛
- **E2E 断言化**
  - 把 Playwright 全链路调试过程沉淀成 `tests/e2e/`，每条流程有断言
  - 保留截图作为失败证据，而不是作为成功证据

### 7.3 预期收益

- 从"跑完就算过"变成"断言就是文档"
- 回归范围更可控
- 覆盖率可追踪可下钻

## 8. 工程化与交付优化

### 8.1 现状

- `requirements.txt` 未锁版本。
- 没有 CI。
- 没有统一代码格式化 / 静态检查。
- 运行方式仍分散在 README、`run_server.py` 和临时命令中，演示端口与测试端口缺少统一约定。

### 8.2 建议

- **依赖锁定**
  - 使用 `pip-compile`（pip-tools）生成 `requirements.lock`
  - 或迁移到 `poetry` / `uv`
- **CI / CD**
  - GitHub Actions：`lint → unit → smoke → e2e → build`
  - Windows / Linux 双矩阵运行，保证跨平台
- **静态检查**
  - `ruff` 管格式与风格
  - `mypy --strict` 管类型（配合 §4 的 dataclass）
- **任务脚本**
  - 新建 `tasks.ps1` 或 `Makefile`：`test`、`run`、`reset-db`、`demo`
  - 让新人一条命令上手

### 8.3 预期收益

- 新成员不再靠"口述 / 记忆"启动项目
- 每次改动都能在 CI 里自动验证
- 跨机器表现一致

## 9. 安全与合规优化

### 9.1 现状

- `SECRET_KEY` 默认值为字面量：
  - `app.config["SECRET_KEY"] = os.environ.get("DRG_APP_SECRET", "drg-ui-prototype-secret")`
  - 未配置环境变量时仍可启动，但会话密钥可预测。
- 未启用 CSRF 保护。
- 登录无失败次数限制。
- 病例删除是物理删除，不可恢复。
- 文档下载有路径校验，但没有**访问日志**。

### 9.2 建议

- **SECRET_KEY 管理**
  - 生产模式下必须读取环境变量，否则启动失败
  - 通过 `FLASK_ENV=production` 区分
- **CSRF**
  - 引入 `Flask-WTF`，对所有 POST 表单加 `csrf_token`
  - 关键操作（删除）必须走 POST 并带 token（现有删除确实是 POST，补齐 token 即可）
- **登录限流**
  - 同一用户名或 IP 连续失败 N 次后临时封锁（可写入 `login_attempts` 表或用内存计数）
- **软删除**
  - `drg_cases` 增加 `deleted_at` 字段
  - 删除路由改为"标记删除"
  - 列表默认过滤 `deleted_at IS NULL`
  - 保留恢复入口（管理员专用）
- **下载审计**
  - 对 `/documents/<id>/download` 记录：用户、时间、文档 ID、来源 IP
  - 落到 `audit_logs` 表（见 §10）

### 9.3 预期收益

- 符合"教学系统也该具备基本审计"的底线
- 管理员误删可追溯可恢复
- 生产部署不再因默认密钥泄漏风险上线

## 10. 可观测性优化

### 10.1 现状

- 没有 logging 配置，全部信息依赖 flash 和控制台 stdout。
- 错误通常只通过 `flash` 对用户可见，后端不留痕。
- 没有审计表。

### 10.2 建议

- **标准日志**
  - 启用 Python `logging`，按模块创建 logger
  - 配置两套 handler：控制台 + 文件（`instance/logs/app.log`）
  - 按级别切分：INFO 记流程、WARNING 记业务异常、ERROR 记异常栈
- **错误统一处理**
  - 用 `@app.errorhandler(Exception)` 捕获未知异常
  - 记录堆栈，返回友好页面
- **审计表**
  - 新建 `audit_logs`：`id, user_id, action, target_type, target_id, payload_json, created_at, ip`
  - 删除、下载、登录失败、权限拒绝 都写入
- **错误监控（可选）**
  - 若上生产可接 Sentry / Glitchtip

### 10.3 预期收益

- 线上出问题不再靠"再现一遍"
- 管理员操作有完整可审计回放

## 11. 可扩展性远期方向

这一节是"如果这个项目不止是课程作业"的方向，全部是可选项。

- **多项目支持**：当前默认只有一个 project，`get_project()` 直接取第一条；要支持多项目需要引入"当前项目"概念。
- **异步任务**：若病例批量导入或规则批量回放成为需求，可引入 RQ / Celery。
- **缓存层**：分布统计、规则加载结果可以进 Redis / 内存缓存。
- **外部规则服务**：接真实的 CHS-DRG 规则服务，把 `rules/` 模块抽象成 Provider 接口。
- **多租户 / 医院级隔离**：在项目之上再加一层 `organization`，权限按 org 级别划分。

## 12. 优化优先级建议

### 12.1 短期（1–2 轮迭代内，成本低收益大）

- 给 `local_llm_corpus.json` 增加 schema 校验、启动告警和热重载入口（§5）
- 把 `smoke_test.py` 拆分并把 Playwright 流程沉淀为可重复执行的断言化 E2E（§7）
- `SECRET_KEY` 生产模式强校验（§9）
- 下载 / 删除等关键动作补审计日志（§9、§10）
- 建立 `tasks.ps1` 统一运行方式（§8）

### 12.2 中期（需要一次成体系的重构）

- `app.py` 按领域拆 Blueprint（§3）
- 抽 `rules/` 与 `repositories/`（§3、§4）
- DRG 规则配置化到 JSON，并逐步把本地微型LLM模式参数也纳入配置（§5）
- smoke 迁移到 pytest + 覆盖率（§7）
- CI 接入（§8）
- 软删除 + 审计日志（§9、§10）

### 12.3 远期（有真实落地场景再考虑）

- 引入轻量 ORM（§4）
- 登录限流、CSRF 全站（§9）
- 多项目 / 多租户（§11）
- 外部真实 DRG 规则服务接入，或引入按项目隔离的本地知识语料（§11）

## 13. 结语

当前项目在"课程交付"维度已经是完整闭环；本文档讨论的是它向"工程化可维护系统"迈进时可以走的路径。

每一条建议都对应具体文件或函数，且互相之间解耦，可以按优先级分批推进，不必整体重构。

推进建议的节奏：

- **先补测试再做架构重构**：测试先行可以兜住后续重构不出回归。
- **先抽规则与语料配置再拆 Blueprint**：配置先稳定，后续拆模块时风险更小。
- **先审计再做软删除**：审计表建好之后，软删除等写操作都能接进来。

按这个顺序，项目可以从"可演示 / 可答辩"稳步走到"可维护 / 可演进"，同时保留当前已经跑通的所有能力。

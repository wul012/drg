# 实验：软件架构

## 一、实验目的

1. 熟悉前后端分离模式下的软件架构思想，理解前端页面、后端服务和数据库之间的职责划分。  
2. 实现前端与后端之间的通信，掌握页面表单提交、路由跳转和后端接口处理的基本流程。  
3. 实现后端与数据库之间的通信，理解后端如何通过 SQL 对数据进行增删改查。  
4. 结合本项目完成一个类似《Todos》的前后端分离实验，不过本项目不是普通待办事项系统，而是一个医保 DRG 智能协同平台，主要围绕需求分析、DRG 病例入组、文档生成、测试用例和提交中心展开。

## 二、实验项目说明

本次实验我使用的是当前的 `drg-ui-prototype` 项目。这个项目是一个基于 Flask + SQLite 的医保 DRG 智能协同平台。虽然它不是传统意义上 Vue 或 React 独立前端加后端 API 的完全分离项目，但是从架构职责上看，它仍然可以分为前端表现层、后端业务层和数据库持久层。

项目中的主要文件结构如下：

```text
drg-ui-prototype/
├── app.py                    # Flask 后端主程序，包含路由、业务逻辑、数据库访问
├── drg_case_utils.py          # DRG 病例筛选、排序、分页和统计辅助函数
├── local_llm.py               # 本地微型 LLM 文本生成逻辑
├── run_server.py              # 项目启动入口
├── templates/                 # 前端 HTML 模板页面
│   ├── base.html
│   ├── index.html
│   ├── login.html
│   ├── dashboard.html
│   ├── analysis.html
│   ├── cases.html
│   ├── documents.html
│   ├── tests.html
│   ├── submit.html
│   └── mobile_*.html
├── static/                    # 静态资源
│   ├── css/style.css
│   └── js/app.js
├── instance/                  # SQLite 数据库和本地产物目录
│   ├── drg_platform.db
│   ├── virtual_docs/
│   └── submissions/
└── tests/                     # 自动化测试文件
```

在普通 Todos 实验中，核心对象通常是 `todo`，也就是待办事项；而在本项目中，核心对象更复杂，主要包括项目、用户、分析结果、DRG 病例、文档、测试用例、提交记录和移动端上报。虽然业务对象不同，但是它们的架构思想是一致的：前端负责输入和展示，后端负责处理逻辑，数据库负责保存数据。

## 三、系统总体架构

本项目可以理解为三层架构：

```text
用户浏览器
   ↓
前端页面层 templates + static
   ↓ HTTP 请求 / 表单提交
Flask 后端 app.py
   ↓ SQL 操作
SQLite 数据库 instance/drg_platform.db
```

### 1. 前端表现层

前端页面主要放在 `templates/` 目录下，样式文件放在 `static/css/style.css`，少量前端脚本放在 `static/js/app.js`。

例如：

- `templates/index.html`：首页
- `templates/login.html`：登录页
- `templates/dashboard.html`：工作台
- `templates/analysis.html`：需求分析页
- `templates/cases.html`：DRG 病例录入和分析页
- `templates/documents.html`：文档中心
- `templates/tests.html`：测试用例中心
- `templates/submit.html`：提交中心
- `templates/mobile_home.html`、`mobile_report.html` 等：移动端页面

前端页面的主要作用是展示数据和接收用户输入。例如在 `templates/cases.html` 中，页面提供了患者姓名、电子病历摘要、主诊断编码、主诊断名称、次诊断编码列表、主手术编码和主手术名称等输入框。用户点击“执行DRG入组”后，页面会把表单数据提交到后端的 `/cases` 路由。

### 2. 后端业务层

后端核心代码集中在 `app.py`。这个文件中包含了：

- Flask 应用创建
- 路由定义
- 登录注册逻辑
- 角色权限控制
- DRG 规则匹配逻辑
- 数据库连接与 SQL 操作
- 文档、测试、提交和移动端上报逻辑

项目中主要路由包括：

| 路由 | 方法 | 功能 |
|---|---|---|
| `/` | GET | 首页 |
| `/login` | GET / POST | 用户登录 |
| `/register` | GET / POST | 用户注册 |
| `/dashboard` | GET | 工作台 |
| `/analysis` | GET / POST | 需求分析 |
| `/cases` | GET / POST | DRG 病例列表与病例提交 |
| `/cases/<int:case_id>/delete` | POST | 管理员删除病例 |
| `/agents` | GET | Agent 协作消息 |
| `/documents` | GET | 文档中心 |
| `/documents/<int:document_id>/download` | GET | 文档下载 |
| `/tests` | GET / POST | 测试用例中心 |
| `/submit` | GET / POST | 提交中心 |
| `/mobile/home` | GET | 移动端首页 |
| `/mobile/report` | GET / POST | 移动端上报 |
| `/mobile/messages` | GET | 移动端消息 |
| `/mobile/documents` | GET | 移动端文档 |

这些路由体现了后端作为“控制层”的作用。前端页面并不直接操作数据库，而是通过访问这些路由，由后端完成参数校验、业务处理和数据库写入。

### 3. 数据库持久层

数据库使用 SQLite，数据库文件路径在 `app.py` 中定义为：

```python
DATABASE_PATH = INSTANCE_DIR / "drg_platform.db"
```

后端通过 `get_db()` 函数连接数据库：

```python
def get_db() -> sqlite3.Connection:
    if "db" not in g:
        connection = sqlite3.connect(app.config["DATABASE"])
        connection.row_factory = sqlite3.Row
        g.db = connection
    return g.db
```

这个函数说明后端会在一次请求中复用数据库连接，并且通过 `sqlite3.Row` 让查询结果可以像字典一样使用字段名访问。

项目中的主要数据库表包括：

| 表名 | 作用 |
|---|---|
| `users` | 保存用户账号、密码哈希和角色 |
| `projects` | 保存项目名称、阶段、描述等信息 |
| `analyses` | 保存需求分析结果 |
| `drg_cases` | 保存 DRG 病例和入组结果 |
| `agents` | 保存 Agent 状态 |
| `messages` | 保存桌面端和移动端消息流 |
| `documents` | 保存文档内容和文档路径 |
| `test_cases` | 保存测试用例 |
| `submissions` | 保存提交批次 |
| `mobile_reports` | 保存移动端上报内容 |

这部分对应实验目的中的“后端与数据库通信”。后端通过 SQL 的 `SELECT`、`INSERT`、`UPDATE`、`DELETE` 来读取和修改数据。

## 四、前后端通信实现

本项目中的前后端通信主要通过 HTTP 请求和 HTML 表单实现。

以 DRG 病例录入为例，前端页面是 `templates/cases.html`，后端路由是 `app.py` 中的：

```python
@app.route("/cases", methods=["GET", "POST"])
@login_required
def cases_page():
```

当用户第一次打开 `/cases` 页面时，浏览器发送 GET 请求，后端读取数据库中的病例列表，然后通过 `render_template("cases.html", ...)` 把数据传给前端页面展示。

当用户填写病例表单并点击“执行DRG入组”时，浏览器会发送 POST 请求。后端通过 `request.form.get()` 获取前端传来的字段，例如：

```python
patient_name = request.form.get("patient_name", "").strip()
record_text = request.form.get("record_text", "").strip()
primary_diagnosis_code_raw = request.form.get("primary_diagnosis_code", "")
primary_diagnosis_name = request.form.get("primary_diagnosis_name", "").strip()
secondary_diagnosis_raw = request.form.get("secondary_diagnosis_codes", "").strip()
procedure_code_raw = request.form.get("procedure_code", "")
procedure_name = request.form.get("procedure_name", "").strip()
```

这就完成了从前端到后端的数据传递。后端处理完数据后，再通过 `redirect(url_for("cases_page"))` 跳转回病例页面，让用户看到最新的入组结果。

我理解这里和 Todos 实验中的新增待办事项类似：Todos 是前端提交一个待办事项标题，后端保存到数据库；本项目是前端提交一个病例，后端完成 DRG 分组并保存到数据库。

## 五、后端与数据库通信实现

后端拿到病例数据后，会进行校验、规则匹配和数据库写入。

在 `/cases` 路由中，后端先校验患者姓名、病历摘要、诊断名称、手术名称等字段是否为空。如果校验通过，就会调用 `build_case_record()` 生成病例记录，然后执行 SQL 插入到 `drg_cases` 表。

项目中的插入逻辑类似下面这样：

```python
database.execute(
    """
    INSERT INTO drg_cases (
        project_id, case_code, patient_name, diagnosis, drg_code, status, risk_level, note, created_at,
        record_text, primary_diagnosis_code, primary_diagnosis_name, secondary_diagnosis_codes_json,
        procedure_code, procedure_name, mdc_code, mdc_name, adrg_code, adrg_name, drg_name,
        complication_level, group_reason, updated_at
    )
    VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
    """,
    (...)
)
```

这里我注意到 SQL 使用了参数占位符 `?`，不是直接拼接字符串。这样可以减少 SQL 注入风险，也让数据写入更加规范。

病例写入后，后端还会更新项目阶段：

```python
database.execute(
    "UPDATE projects SET phase = ?, updated_at = ? WHERE id = ?",
    ("DRG入组已更新", now_str(), project["id"]),
)
```

最后调用：

```python
database.commit()
```

提交事务，使数据真正写入 SQLite 数据库。

## 六、DRG 业务逻辑与架构结合

这个项目不是简单的 Todo 列表，它的业务核心是 DRG 分组。DRG 规则主要写在 `app.py` 中，例如：

```python
SIMPLIFIED_MDC_RULES = [ ... ]
SIMPLIFIED_ADRG_RULES = { ... }
SIMPLIFIED_MCC_CODES = {"J96", "I50", "N17", "R57", "A41"}
SIMPLIFIED_CC_CODES = {"E87", "D64", "I10", "N39", "J18"}
```

其中：

- `SIMPLIFIED_MDC_RULES` 用来根据主诊断编码匹配 MDC 大类。
- `SIMPLIFIED_ADRG_RULES` 用来根据 MDC 和手术编码匹配 ADRG。
- `SIMPLIFIED_MCC_CODES` 和 `SIMPLIFIED_CC_CODES` 用来判断严重并发症或一般并发症。
- `DIAGNOSIS_NAME_CODE_MAP` 和 `PROCEDURE_NAME_CODE_MAP` 支持无编码病例根据名称自动补码。

DRG 分组的大致流程是：

```text
前端提交病例
   ↓
后端读取主诊断、次诊断、主手术
   ↓
根据诊断名称/手术名称补充编码
   ↓
匹配 MDC
   ↓
匹配 ADRG
   ↓
判断 CC / MCC
   ↓
生成 DRG 编码、名称、风险等级和原因说明
   ↓
写入 drg_cases 表
   ↓
刷新文档、测试用例和 Agent 消息
```

例如前面项目中已经支持无编码样例：当前端只填写“胃窦恶性肿瘤”和“腹腔镜胃大部切除伴胃空肠吻合术”时，后端可以通过名称映射得到：

```text
胃窦恶性肿瘤 -> C16.301
腹腔镜胃大部切除伴胃空肠吻合术 -> 43.7X03
```

然后系统可以分组为：

```text
MDCG -> GB2 -> GB29
```

这说明后端不仅完成普通增删改查，还包含了业务规则计算。

## 七、病例列表的查询、筛选和分页

在 Todos 实验中，通常需要查看所有待办事项，也可能需要根据完成状态筛选。当前 DRG 项目中也有类似功能，只是筛选条件更多。

病例辅助逻辑放在 `drg_case_utils.py` 中，例如：

- `filter_drg_cases()`：根据 MDC、风险等级、状态和关键词筛选病例
- `sort_drg_cases()`：根据创建时间、风险等级、病例编号排序
- `paginate_items()`：分页显示病例
- `compute_distribution()`：统计分布数据

其中 `filter_drg_cases()` 会检查病例编号、患者姓名、诊断、手术编码、手术名称等字段是否包含关键词。这和 Todos 中按关键词搜索待办事项很像，只是这里搜索的是 DRG 病例业务数据。

在 `/cases` 路由中，后端会读取 URL 查询参数：

```python
mdc_filter = request.args.get("mdc", "").strip().upper()
risk_filter = request.args.get("risk", "").strip()
status_filter = request.args.get("status", "").strip()
keyword = request.args.get("q", "").strip()
sort_value = request.args.get("sort", "created_desc").strip()
```

然后把筛选后的结果传给 `cases.html` 页面展示。这样就实现了前端筛选条件和后端查询逻辑之间的通信。

## 八、文档、测试和提交中心的联动

本项目比普通 Todos 实验更完整的一点是，它在病例入组后还会联动生成文档、测试用例和提交记录。

例如病例提交成功后，`/cases` 路由中会调用：

```python
sync_generated_content(project["id"], project["name"], get_analysis(project["id"]))
```

这个函数会联动更新文档、测试用例和消息流。文档数据保存到 `documents` 表，同时真实文件会写入 `instance/virtual_docs/` 目录；提交中心生成的提交清单会写入 `instance/submissions/` 目录。

这部分让我理解到，一个系统中的业务操作通常不是孤立的。比如新增一个 Todo 可能只需要写入一张表，而新增一个 DRG 病例会影响病例表、项目状态、文档、测试用例和 Agent 消息。这体现了软件架构中模块协作的重要性。

## 九、移动端与桌面端通信

项目还提供了移动端页面，例如：

- `/mobile/home`
- `/mobile/report`
- `/mobile/messages`
- `/mobile/documents`

移动端上报功能在 `app.py` 中对应路由：

```python
@app.route("/mobile/report", methods=["GET", "POST"])
@login_required
def mobile_report():
```

用户在移动端填写上报标题和内容后，后端会写入 `mobile_reports` 表，同时也会向 `messages` 表写入一条消息。这样 PC 端的 Agent 协作页面就可以看到移动端同步过来的内容。

我认为这也是一种前后端通信和多端协作的体现：移动端页面和 PC 端页面虽然展示形式不同，但它们都通过同一个 Flask 后端和同一个 SQLite 数据库进行数据交换。

## 十、与 Todos 实验的对应关系

虽然本项目不是传统 Todos，但是它和 Todos 实验的架构目标是一致的。可以这样对应理解：

| Todos 实验 | 当前 DRG 项目 |
|---|---|
| Todo 项 | DRG 病例、文档、测试用例、移动端上报 |
| 新增 Todo | 新增 DRG 病例或移动端上报 |
| 查询 Todo 列表 | 查询病例列表、文档列表、消息列表 |
| 修改 Todo 状态 | 更新项目阶段、病例状态、提交状态 |
| 删除 Todo | 管理员删除病例 |
| 前端调用接口 | 页面表单 GET / POST 请求 Flask 路由 |
| 后端操作数据库 | `app.py` 使用 sqlite3 操作 SQLite |

所以我认为本项目相当于一个业务更复杂的 Todos 实验。它不仅实现了基础的增删改查，还加入了权限控制、业务规则、文档生成、测试生成和移动端协同。

## 十二、实验总结

通过本次实验，我对软件架构中的前端、后端和数据库分层有了更加具体的理解。

在这个 DRG 项目中，前端页面主要由 `templates/` 和 `static/` 组成，负责展示页面和接收用户输入；后端主要由 `app.py` 负责，处理登录、需求分析、病例入组、文档、测试、提交和移动端上报等业务逻辑；数据库使用 SQLite，通过 `instance/drg_platform.db` 保存系统数据。

我印象比较深的是 `/cases` 这个功能。它完整体现了前后端通信和后端数据库通信的过程：用户在前端填写病例，后端接收表单数据，调用 DRG 规则进行分组，然后把结果写入数据库，最后页面重新显示最新结果。这条链路比普通 Todos 的新增待办事项更复杂，但是架构思想是一样的。

通过分析这个项目，我也认识到软件架构不是单纯把代码写出来，而是要考虑不同模块之间的职责划分和数据流向。前端不应该直接访问数据库，数据库操作应该由后端统一处理；业务规则也应该集中在后端，这样系统更安全，也更容易维护。

总的来说，本次实验让我从一个真实 DRG 项目中理解了前后端通信、后端数据库访问、模块联动和分层架构的基本思想，也让我对《Todos》这类前后端分离实验有了更深入的认识。

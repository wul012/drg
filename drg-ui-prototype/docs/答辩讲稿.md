# 医保DRG智能协同平台答辩讲稿

## 1. 开场介绍

各位老师好，我们小组本次课程项目的题目是“医保DRG智能协同平台”。

这个项目最初是一个偏原型化的展示系统，后续我们把它升级为了一个真正可以运行的课程项目实现。我们的目标不是做一个生产级 DRG 商业系统，而是在课程实验范围内，完成一个可以真实演示、可以真实写库、可以形成业务闭环的教学版平台。

项目采用 Flask + SQLite 技术路线，支持桌面端和移动端协同，覆盖了需求分析、DRG 病例入组、多 Agent 协作、文档自动生成、测试用例生成、提交中心和消息同步等核心能力。

## 2. 设计思路说明

在实现策略上，我们采用的是“可运行实现 + 内置简化规则 + 本地规则/模板驱动”的方案。

这样做的原因主要有三点。

第一，课程项目时间有限，而真实 DRG 分组依赖大量完整编码规则和专业数据，直接做生产级实现难度过高。

第二，如果只停留在静态原型层面，系统虽然好看，但无法证明业务真正跑通。

第三，我们希望最终成果既能体现业务理解，又能在现场稳定演示，所以选择用教学版规则完成一个完整、可解释、可运行的业务闭环。

## 3. 系统核心功能

下面我介绍一下系统的几个核心模块。

### 3.1 需求分析模块

用户可以录入项目名称、需求背景、目标和优先级。系统会基于这些信息生成需求摘要、核心模块建议、风险识别和推荐行动，并把结果写入数据库。

在当前版本中，需求分析页还增加了本地微型LLM的模式切换，支持严谨模式、平衡模式和增强模式。切换模式后，分析结果、文档和测试用例会整体联动刷新。

### 3.2 DRG 入组模块

这是本项目最核心的业务模块之一。用户可以在页面录入病例摘要、主诊断、次诊断和主手术信息。系统会基于内置教学版规则输出 MDC、ADRG、DRG、并发症层级、风险等级以及入组原因说明。

这部分的重点不是追求真实医保生产准确率，而是展示 DRG 分组的基本思路、规则匹配链路和可解释结果。

为了让“可解释结果”更像本地智能生成系统，我们还加入了一个纯 Python 的本地微型LLM，让 DRG 入组原因说明可以在规则事实不变的前提下输出更自然、更适合展示的解释文本。

### 3.3 多 Agent 协作模块

系统中设计了多个角色化 Agent，包括需求分析 Agent、DRG 分析 Agent、文档生成 Agent、测试用例 Agent 和提交 Agent。它们的状态和消息流都会展示在页面中。

这里的 Agent 不是接入外部大模型，而是基于本地模板和业务状态驱动的协作机制，目的是模拟协同平台中的职责分工与流程联动。

### 3.4 文档自动生成模块

系统会根据需求分析和 DRG 结果自动生成需求分析文档、架构设计文档和测试文档。每份文档不仅写入数据库，还会同步写入本地虚拟文档目录。

在最新版本中，文档正文也已经复用了本地微型LLM，因此除了结构稳定之外，文风会随着当前模式发生变化。

### 3.5 测试用例生成模块

系统可以自动生成正常、边界和异常三类测试用例，并在页面中展示测试编号、功能点、前置条件、测试步骤、预期结果和优先级。

测试文案同样接入了本地微型LLM，所以不仅能保持结构稳定，也能体现“更严谨”或“更适合答辩展示”的不同表达风格。

### 3.6 虚拟文档系统与提交模块

用户可以在提交中心勾选文档并执行提交。提交后，系统会更新文档状态，生成提交批次，生成本地提交清单，并写入历史提交记录。

这部分体现了项目从“内容生成”走向“结果留痕”的完整闭环。

## 4. 现场演示讲解词

接下来如果现场演示，我会按照下面的顺序讲解。

第一步，进入系统首页并登录。这里我会说明系统提供默认演示账号，并且登录后可以进入完整的桌面端业务工作台。

第二步，先进入需求分析页面，把本地微型LLM切换到“增强模式”，并说明这个模式会影响分析结果、文档和测试文案的表达风格。

第三步，进入 DRG 分析页面，展示病例录入表单。我会说明这里不是纯展示，而是真正可以提交数据并触发入组逻辑。

第四步，录入一条病例，例如主诊断 `A01.002+G01`、次诊断 `J96.0`、主手术 `38.1000X002`。提交后，系统会输出对应的 MDC、ADRG 和 DRG，并展示入组原因说明。这样可以证明本地教学版规则已经真正运行起来。

第五步，进入文档中心，展示系统根据当前项目和病例结果自动生成的需求文档、架构文档和测试文档。同时展示来源智能体、接收时间、本地存储路径以及当前本地微型LLM模式。

第六步，进入测试中心，展示自动生成的正常、边界和异常三类测试用例，说明测试模块并不是固定表格，而是会跟随当前系统状态联动刷新。

第七步，进入提交中心，勾选文档后执行提交。这里我会强调系统不只是修改页面状态，而是会真实写入提交批次和本地提交清单文件。

第八步，进入 Agent 协作页面，展示多个 Agent 的当前状态和消息流，说明 DRG 入组、文档生成、测试刷新和提交留痕之间已经形成完整的业务消息链。

## 5. 项目亮点总结

我认为这个项目有以下几个亮点。

第一，项目不是静态原型，而是具备真实业务流和数据库写入能力的可运行系统。

第二，项目围绕课程实验进行了合理简化，既保留了 DRG 和协同平台的业务特征，又避免了无法在课程周期内完成的生产级复杂度。

第三，项目具备较好的展示效果。首页、工作台、文档中心、提交中心和移动端页面都做了统一风格优化，更适合答辩展示。

第四，项目具有较好的可解释性。尤其是在 DRG 入组结果上，不仅给出编码结果，也给出规则匹配原因。

第五，项目形成了完整闭环：需求分析推动病例处理，病例结果推动文档生成，文档生成推动测试覆盖，最后进入提交留痕。

## 6. 如果老师追问“为什么不用真实 DRG 规则”

如果老师问为什么没有使用真实完整的 DRG 规则，我会这样回答：

真实 DRG 分组依赖大规模标准编码表、专业规则库和更复杂的临床上下文。在课程项目条件下，如果直接追求生产级精度，反而很容易导致系统做不完、演示不稳定。

因此我们采用了教学版简化规则，把重点放在“业务闭环是否跑通”“规则链路是否可解释”“系统是否可运行”这三个更符合课程实验评价目标的维度上。

## 7. 如果老师追问“Agent 是不是真的 AI”

如果老师问 Agent 是否是真正的大模型智能体，我会回答：

本项目中的 Agent 采用的是本地模板驱动和状态驱动机制，不依赖外部大模型服务。这样设计的原因是为了保证系统可离线运行、可稳定演示、可控且易于理解。

虽然它不是生产环境中的 LLM Agent，但它已经完成了课程项目中“多角色协作”和“业务联动”的展示目标。

## 8. 结束语

最后总结一下。

本项目已经完成了从需求分析到 DRG 入组、从文档生成到测试覆盖、从提交留痕到 Agent 协作展示的完整业务链路，并且所有关键页面和功能都可以在本地环境中真实运行。

因此，我们认为这个系统已经满足课程项目对于“业务完整性、系统可运行性、功能可展示性和实现合理性”的要求。

我的汇报到这里结束，谢谢各位老师。

## 9. 功能增强说明

在基础版本之外，我们还针对课程评分维度进行了两轮主动增强。这两轮增强不仅提升了系统的可展示性，也补齐了工程化要求。

### 9.1 第一轮：规则覆盖、删除与权限

第一件事是扩展了 DRG 规则的覆盖面。原本系统只支持神经、呼吸、消化和代谢四类 MDC，现在增加了循环系统 MDCE 和泌尿系统 MDCL，并为这两类补充了对应的 ADRG 手术组和内科治疗组。这样在现场演示时就可以录入例如 I21.0 急性心肌梗死并执行冠状动脉搭桥手术，得到 MDCE → FB1 → FB13 的完整入组链路，体现规则的可扩展性。

第二件事是补齐了 CRUD 中缺失的删除能力。我们在 DRG 分析页面的历史列表中增加了“撤销该病例”的按钮，撤销后系统会同步刷新 Agent 状态、消息流、文档和测试用例，保持业务一致性。

第三件事是真正做了一层角色权限。通过自研的 role_required 装饰器，只有“管理员”角色才能执行删除操作，分析员和医生角色在页面上看不到删除按钮，即便绕过前端直接 POST 请求，后端也会返回权限警告并阻止删除。

### 9.2 第二轮：筛选、下载与分布可视化

第一件事是给病例列表增加了 MDC 大类筛选和多字段关键词搜索，关键词会同时匹配病例编号、患者姓名、主诊断、主手术等字段。在病例逐渐增多时，这个能力可以显著提升管理效率。

第二件事是让虚拟文档系统真正“看得见、下得动”。我们在文档中心为每份文档增加了“下载原文件”按钮，点击后会直接返回 instance/virtual_docs 下的原始文本，浏览器可以像下载普通文件一样保存它。这证明虚拟文档不是假落盘。

第三件事是让工作台首页具备数据可视化能力。我们新增了“DRG 入组分布”面板，用纯 HTML 和 CSS 实现了三组条形图：MDC 大类分布、风险等级分布、状态分布。没有使用任何外部图表库，因此加载速度快、展示稳定。

### 9.3 第三轮：本地微型LLM与模式切换

第三轮增强主要解决“系统虽然能跑，但还不够像本地智能系统”的问题。

第一件事是新增 `local_llm.py`，实现纯 Python 的本地微型LLM，不依赖任何外部 API。它主要采用小语料 + n-gram 风格生成的方式，在规则事实不变的前提下，把 DRG 原因说明、需求分析、文档正文和测试文案写得更自然。

第二件事是把扩展语料落到 `local_llm_corpus.json` 外部文件中。这样后续如果要继续增强文风，不需要改核心逻辑，只需要直接补语料文件即可。

第三件事是在需求分析页加入了三档模式切换：严谨模式、平衡模式和增强模式。切换后，下游生成内容会整体刷新。这样在答辩时，如果老师更关注工程严谨性，可以切到严谨模式；如果更关注展示效果，可以切到增强模式。

第四件事是在分析页、病例页、文档页和测试页都加上了“本地微型LLM · 当前模式”的轻量标识，让评审老师能一眼看出这部分能力已经真正接入界面，而不是只写在文档里。

### 9.4 工程化验证

为了让上述增强具备“可验证”特征，我们补齐了两类自动化测试。

其一是纯函数单元测试。我们新建了 tests/test_drg_rules.py，共 15 条用例，覆盖 match_mdc、match_adrg、detect_complication_level、group_drg_case 这四个核心函数在六个 MDC 大类和 CC / MCC / 无并发症三种情形下的行为。运行命令是 python tests/test_drg_rules.py，15 条用例全部通过。

其二是本地微型LLM专项测试。tests/test_local_llm.py 现在覆盖 DRG 原因说明保留核心事实、需求分析结构完整、文档引用最新病例、测试用例结构稳定，以及模式与外部语料文件元信息加载等能力。

其三是集成级别的冒烟测试。smoke_test.py 现在会覆盖登录、需求分析增强模式切换、DRG 入组、本地微型LLM标识、提交闭环和移动端上报同步等关键路径。运行命令是 python smoke_test.py，最终输出 “Smoke tests passed.”。

除此之外，我们还用 Playwright 从首页重新走了一遍完整链路，实际验证了增强模式下的分析页、病例页、文档页、测试页和提交中心都能正常工作，而且浏览器控制台错误数为 0。

这两套测试不依赖任何第三方测试框架，完全使用标准库实现。这意味着只要有 Python 和 Flask，任何评审老师都可以直接复现结果。

## 10. 如果老师追问“你这些增强的工程价值是什么”

如果老师问这些增强为什么值得做，我会这样回答：

第一，规则扩展让系统从“只演示 4 个大类”变成“具备按需扩展规则目录的能力”，这对应课程对“业务引擎可扩展性”的要求。

第三，筛选、下载和分布可视化让系统从“能跑”变成“能被用户长期使用”，这对应课程对“可用性和产品完整度”的要求。

第四，单元测试和冒烟测试让系统从“本次跑通”变成“以后改动也不会回退”，这对应课程对“工程质量”的要求。
